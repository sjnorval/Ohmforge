# Ohmforge project rules (Grok Build)

Grok Build also reads the root `AGENTS.md`; that file is the full guide and wins on any conflict. Short version:

1. Source of truth: `docs/DESIGN_AND_PLAN.md` (never edit it unless Stefan asks). Current tasks: `docs/ROADMAP.md`. Schematic wire routing: `docs/design/wire-routing.md`. Base engine and plug-in components (E1 to E3 done in P2; E4 to E6 in P3, #48 to #50; PSU return #45 done): `docs/design/engine-components.md`; once the engine API exists, every new part is a component on it (ESP32-C3 and PSU included), with no per-demo glue and no hidden ground connections. Circuit files: `*.circuit.toml` (RFC 0003, crate `of-circuit`, files in `circuits/`, CC-BY-SA-4.0); firmware by path and SHA-256 only; keep them canonical with `ohmforge circuit fmt` and check them with `ohmforge circuit check` (CI runs both on `circuits`). The desktop demos are `circuits/demos/*.circuit.toml`; they give the ESP32-C3 its datasheet supply current (`quiescent_a`: 23 mA running, 16 mA in `wfi`, at 160 MHz; ESP32-C3 datasheet v2.5 Table 5-8), and parity runs switch it off. Their schematic comes from the file (`wiring::from_circuit`; its routes must match the wiring goldens byte for byte). Since E4d the desktop runs them on `Session` (`of-ui` `SessionSim`) as its only path: no flag, and the hand-wired boards and simulations are deleted. Trace goldens are blessed from the circuit files (`parity`; `OF_BLESS=1` on Linux), and the registry-built `Session` must match the files at the strict tolerance. Engine runtime (E4b): build circuit files with `of_circuit::build::build` (firmware through a `Resolver`: `FsResolver` with `with_rom` on the host, `EmbeddedResolver` in apps; `of_circuit::demos` embeds the demos), build parts through `of_engine::Registry` (`of_components::register_builtin`, `of_soc_esp32c3::register`) and run them with `Session`; `ohmforge run <file.circuit.toml>` runs one headless; trace parity goldens are in `crates/of-ui/src/parity/goldens/` (re-record only with `OF_BLESS=1` on Linux and a reviewed diff; accepted parity exceptions are listed in RFC 0003). Measurement (E5, #49, RFC 0004 Draft): signals are named as in `[[probe]]` (`v(net)`, `v(a,b)`, `i(R1)`, `i(U1.pin)`, `r(REF.reading)`, `d(REF.pin)`); `of_instruments::MeasurementService` samples them from a `Probeable` into `TraceBuf` rings, and the sample ring, `SampleClock` and statistics live in `of_instruments::{ring, stats}` (`of-ui::trace` keeps only time/div and formatting); instruments default to the ideal profile, and real-world profiles use cited datasheet figures only. Arduino-ESP32 / ESP-IDF MVP demos (#60): `docs/design/arduino-idf-mvp-demos.md` (design before firmware; not the P4 Arduino IDE board package).
2. Current phase: **P2 (ESP32-C3 MVP) is in progress**; P1 Analog core is complete. P2 so far: ELF and ESP flash image loading (`of-firmware`), the C3 memory map, GPIO/IO MUX, UART0 TX, SYSTIMER with alarms, the interrupt matrix, TIMG0/1 and the watchdogs, and `Esp32c3Engine` (`of-soc-esp32c3`, `AGENTS.md` section 3c), with the blinky firmware in `firmware/` driving an LED end to end and a timer-interrupt firmware; the SPI flash, cache MMU, real-ROM boot (`power_on_rom`, esp-rom-elfs), ROM-lite flash boot (`boot_flash`), partition tables and the XIP blinky (`firmware/esp32c3-xip-blinky`) are on `main`; an unmodified esp-hal blinky (`firmware/esp32c3-esp-hal-blinky`) boots through the real ROM and espflash's ESP-IDF bootloader (fetched with the ROM, never committed; `tests/esp_hal_blinky.rs`) on `main`, with the CPU clock (`system`), RNG, PMP and trigger CSRs and RTC calibration; GPIO inputs are on `main` (#22) (V_IH/V_IL watches into `input_code` events, `FUN_IE`, 45 kΩ pulls in `PinOut::thevenin`, pin interrupts on matrix sources 16/17, exact-time input reads via `Bus::defer_load` and lazy `wfi`; AGENTS.md section 3c), the `switch` analog kind with `generic.pushbutton`, and `firmware/esp32c3-esp-hal-button` (polling and interrupt apps, `tests/esp_hal_button.rs`); the SAR ADC one-shot mode (`saradc`: conversions sample the circuit at their start via `Esp32c3Engine::link_adc` and `AnalogEngine::sample_on`, codes from the eFuse calibration) and LEDC PWM (`ledc`: exact-time PWM edges through GPIO matrix signals 45 to 50, no averaging), the `potentiometer` analog kind with `bourns.ptv09a-b103`, and `firmware/esp32c3-esp-hal-adc-pwm` (pot dimmer and LED fade, `tests/esp_hal_adc_pwm.rs`) are on `main` (#24), as is UART0 RX FIFO with serial Send delivery (#25); the common-components checklist is `docs/COMPONENTS.md`; the desktop app (`of-app --features gui`) plays the EILIi load screen (packed frames, skip, persistent Show startup animation setting, `--no-splash` / `OF_NO_SPLASH`) and is a live demo picker in `of-ui` (LED blink, pot dimmer with a run-time slider via `BuiltBoard::pot_params`, LED fade and push-button; schematic with an averaged on-screen LED, a window-tied current-scope ring with time/div zoom (playback down to 1e-6×), clickable SW1, configurable bench PSU, virtual V/A meters, serial monitor panel over `of-instruments::SerialMonitor` for UART0; #26 and #27). The analog solver holds a settled DC network and the hart caches decoded instructions (`fence.i` I-cache, monomorphised bus, quiescent GPIO batching, #44; busy demos about 0.17–0.23× realtime). The dimmer and fade boot the fetched ROM and espflash bootloader (never bundled; `scripts/fetch-esp-rom-elfs.*`); they do not start from the app image alone, unlike the bare-metal blinky; the C3 hart has no `mie`/`mip` (`HartConfig::mie_mip`). The bench PSU's − terminal is routed to GND and LED/PSU currents are period-averaged (#45, closed by #54). Next steps are in the roadmap's P2 checklist (Arduino and ESP-IDF MVP demos #60 after the design note; remaining engine/UI items as listed). P1 covers `crates/of-analog`, `of-netlist::spice`, `ohmforge run`, the parts bridge `of_components::analog`, `AnalogEngine` under the `of-core` kernel and the AMS1117 macromodel (design notes in `AGENTS.md` section 3b). Phase one, the RISC-V core (`crates/of-cpu-riscv`, section 3a), is done. New analog features need an analytic test and an ngspice golden circuit (`* ngspice-replace:` for Ohmforge-only syntax), all within 1 %; new analog parts also need datasheet checks through the bridge. Register CPU engines before the analog engine.
3. Rust edition 2024, MSRV 1.95. On Windows, load the Build Tools `vcvars64.bat` environment for that machine first (`AGENTS.md` section 9). Then run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, the GUI check and the wasm32 check from `AGENTS.md`.
4. Licence: code is AGPL-3.0-or-later, parts data, circuit files and docs CC-BY-SA-4.0. Dependencies must be AGPL-compatible (the permissive `deny.toml` allow list; no GPL-2.0-only or LGPL); never copy code from QEMU, CircuitJS, SimulIDE or Wokwi. riscv-tests (BSD-3) are built from source, never committed. Espressif's ROM ELFs (esp-rom-elfs: Apache-2.0 files, closed-source ROM code) are fetched by `scripts/fetch-esp-rom-elfs.sh`/`.ps1` (pinned release and SHA-256, cached in `.cache/`), never committed; ROM tests skip without them. ngspice is only ever run as an external tool to make golden CSVs (`scripts/gen-ngspice-golden.sh`); never link, vendor or ship it.
5. Git: report changes to Stefan and propose a commit breakdown; **commit only after his approval**. Commits are signed off (`git commit -s`) Conventional Commits. Remote `origin` is https://github.com/sjnorval/Ohmforge; `main` holds everything merged so far. New work goes on feature branches off `main` and reaches it only through pull requests Stefan merges; never push to `main`. Push only when Stefan says so, never force-push, never handle tokens. Every user-visible change adds a line under `## [Unreleased]` in `CHANGELOG.md`; pull requests follow the checklist in `.github/pull_request_template.md` (sign-off, tests, fmt/clippy/test, cargo-deny, AGPL-compatible deps, no ngspice linking, firmware ELFs rebuilt, docs, `AGENTS.md`, these rules and the roadmap updated) and get type, `phase:*` and `area:*` labels (`CONTRIBUTING.md`). Stacked PRs must be merged bottom-up: retarget each later PR to `main` (`gh pr edit --base main`), confirm it targets `main` before merging, and after each merge verify the tip is on `main`; never merge a later PR into its feature-branch base.
6. **Ohmforge** is the final name; crates use the `of-` prefix.
7. Simulation crates stay deterministic (virtual `SimTime`, no wall-clock) and wasm32-compatible.
