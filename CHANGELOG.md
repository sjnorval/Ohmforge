# Changelog

All notable changes to Ohmforge are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project will use [Semantic Versioning](https://semver.org/) from its first release (0.1, the end of P2; see [`docs/ROADMAP.md`](docs/ROADMAP.md)).

Add a line under **Unreleased** in every pull request with a user-visible change, in the matching section (Added, Changed, Deprecated, Removed, Fixed, Security). GitHub's generated release notes (`.github/release.yml`) list the pull requests; this file is the curated summary.

## [Unreleased]

Nothing has been released yet. Everything below is on `main` and will ship in 0.1.

### Changed

- **NE555 latch without a capacitor:** the 10 pF on the latch node rang under trapezoidal integration at long steps and could flip the latch early (the astable ran 9 % fast at a 100 µs step); output edges are now instant.
- **Bench supply rating from its load:** the supply warns outside the `vdd`/`vcc` range shared by the parts on its + rail (the circuit builder passes it as `rated_min`/`rated_max`), not a fixed ESP32-C3 3.0 to 3.6 V; the set point now goes to 30 V (a DP832 channel). On a cold start (`[sim] uic`) the supply no longer regulates against the unsolved 0 V rail at t = 0: a commit there read a short, switched to constant current and drove the load far above the set point (or stalled the solver on forward-biased diodes). The supply output is now one nonlinear device (`of_analog::devices::BenchSupply`): CV behind `series_r` or CC at the limit, whichever gives less current, with a smooth corner the stepper lands on; in CC the rail can never rise above the set point (a bare current source regulated only at commits ran away to 24.6 V in a 20 ms test). Parts on one rail with no common supply range get their own warning, and `circuit check` names them (`library::rail_warnings`).
- **PSU readout and scope on the measurement service (engine E5d, #49):** the bench PSU's face (rail voltage, current, CV/CC/off, rating warning, period-averaged current) is now read from the `bench.psu` component's `r(PSU.*)` readings through the measurement service, the LED scope trace is an `of_instruments` scope channel, and the service owns the sample grid the desktop demos step on. The desktop's duplicate supply types are gone (`of_components::psu` holds them). Readings are unchanged: the PSU face and LED average are bit-identical on all five demos and in current limit, and the trace goldens and pinned meter readings did not change.
- **Ideal multimeter (engine E5c, #49):** the desktop voltmeter and ammeter now come from `of_instruments::meter` and read any circuit through the measurement service instead of a per-demo table of nodes and branches (`CircuitReadout` is gone). Both average over whole PWM periods of the LED current, as a real DMM's integrating ADC does (before, only the PSU branch was averaged), falling back to a 2 ms window. An ammeter goes through any part with a pin on both clicked points; when several do, a small *through* chooser in the meter bar lists them (for example U1 / PSU / RV1 between 3V3 and ground), and the meter list shows the part (`via PSU`). **Behaviour change:** pairs that used to say *no single branch joins those points* now offer the ESP32-C3 (U1) wherever it has pins on both nets, and the dimmer's RV1 between 3V3 and ground. On all five demos every meter the old readout resolved shows the same text and value within max(1 nA, 1 ppm), PSU included (table in RFC 0004).
- **Diode current probe (engine E5c, #49):** every diode and LED now reports its current as `i(<name>)` (the series-resistance current, or the Shockley junction current without `rs`), so `terminal_currents` of a diode or LED part is its real current instead of 0, and `ohmforge run` output gains an `i(<diode>)` column. The solution itself is unchanged; on all five demos `i(D1)` agrees with the series resistor's current to within 1e-16 A (trace goldens identical).
- **LED current from the circuit file's probe (engine E5b, #49):** the desktop's LED scope, averages and duty/frequency now read each demo file's `[[probe]] name = "LED current"` signal (`i(R1)` or `i(R2)`) through the measurement service, instead of a hard-coded `(V(GPIO8) − V(LED anode)) / 330 Ω`. The engine `Session` answers any `v(..)`, `i(..)` and `r(..)` signal. Readings are unchanged (the probe matched the old formula exactly on all five demos; trace goldens identical).
- **Measurement-service core (engine E5a, #49):** `of-instruments` now holds the scope's sample ring (`TraceBuf`), the sample grid (`SampleClock`) and the averaging and PWM duty/frequency maths, moved unchanged from `of-ui`, plus min/max and time-weighted RMS, `Signal` names (`v(net)`, `v(a,b)`, `i(R1)`, `r(PSU1.volts)`, `d(U1.GPIO8)`) and a `MeasurementService` that samples watched signals on a grid and at exact events. Readings in the app are unchanged (trace goldens identical). Design in RFC 0004 (Accepted).
- **Circuit files are the desktop's only path (engine E4d, #48):** `of-app` always draws and runs the five demos from the embedded `circuits/demos/` files on the engine `Session`. The `--circuit-files` flag, the `OF_CIRCUIT_FILES` variable and the `circuit_files` preference are gone (an old `circuit_files` key in the config file is ignored). The hand-wired boards and simulations are deleted; the trace goldens are now blessed from the circuit files (unchanged byte for byte), parity compares the registry-built session with the files at the strict tolerance, and the wiring tests check the route goldens. The window title stays "Ohmforge". Fixed on the way: changing the bench PSU before the demo had advanced (for example at t = 0) read the rail solved for the old set point as an overload, switched to constant current and drove the limit into the load for one step (the dimmer's rail showed about 70 V); the `bench.psu` component now keeps its mode until the rail has been solved at the new set point. This completes E4.
- **ESP32-C3 supply current from the datasheet (E4c, #48):** the chip now draws 23 mA from 3V3 with the CPU running at 160 MHz and 16 mA when it sleeps in `wfi` (ESP32-C3 Series Datasheet v2.5, Table 5-8), instead of 5 mA. It is the `Esp32c3Component` default (`QUIESCENT_A`, new `QUIESCENT_WFI_A`), the demo files' `quiescent_a` (0.023; 0.016 for `button-irq`), and the hand-wired desktop boards now draw it too, so the bench PSU reads about 23 mA on blink with the LED off and 27 mA with it on. The hand-wired dimmer also gets the ADC pin's idle pad (1 GΩ, within the datasheet's 50 nA input-current limit), so both desktop paths read the same and the dimmer's 3.5 nA parity exception is gone. Goldens re-recorded: `dimmer` (PSU up to 2.7 nA higher) and `blink.idle-draw` (PSU 23 mA instead of 5 mA above the LED).
- **README roadmap:** replaced the long phase bullets with a short status table and a link to [`docs/ROADMAP.md`](docs/ROADMAP.md). The detailed checklists, including P0 leftovers and the P2 landed work, stay in the roadmap.
- **Realtime (#61):** profiled the busy desktop demos after further hart hot-path work (ALU early-out, empty-breakpoint `run_tight`). Release factors stay about 0.17–0.22× (dimmer ~0.22×, button-poll ~0.17×); 1× needs a faster CPU execution strategy (documented in the roadmap). Dimmer release tests assert a 0.15× floor so #44 does not regress.
- **Desktop window:** the app now opens maximised; restoring it falls back to the 980 × 720 default.
- **Stub crate dependencies:** removed unused dependency lines from empty and placeholder crates, dropped unused `[workspace.dependencies]` path entries, and gated `of-ui`'s `of-instruments` behind the `gui` feature so `cargo check --workspace` stays free of unused-dependency warnings. Planned edges remain in the `AGENTS.md` crate map.

- **Switch events land on their threshold crossings:** the transient solver redoes a step in which a voltage- or current-controlled switch flipped so that it ends just after the control crossed its threshold (within 1e-4 of the maximum step), then restarts the step size as after a corner, so switch timing no longer depends on `max_step`.
- **Cold start for circuit files:** optional `[sim] uic = true` starts a circuit from initial conditions (every net at 0 V, supplies applied at t = 0) instead of an operating point, with optional `[sim] ic` net voltages; `format` stays 1. Circuits with no DC operating point, such as a 555 astable, now run on the desktop engine and in `ohmforge run`.
- **SPICE macromodel parts in circuit files:** every `spice:<file>` model a `subckt` part names (NE555, AMS1117) is registered with the engine, so circuit files can place them.
- **555 demo circuits** (headless for now): `ne555-astable` LED flasher (scope on the timing capacitor and output, meter on the LED current) and `ne555-monostable` button one-shot (scope on TRIG, the capacitor and the output, meter on the LED current); `crates/of-circuit/tests/demos_555.rs` checks the astable period and the 1.1 RC pulse against the RC timing at a 100 µs step.
- **The 555 demos are embedded** (`of_circuit::demos::DEMOS`, with the NE555, 1N4148 and MLCC parts and `ne555.lib` in `demos::MODELS`), so an app builds them without the repository.
- **Desktop session sim runs the 555 demos** (no ESP32, no ROM): three demo kinds on an analog-only sampling loop, starting on the file's 5 V supply, with the pot (PWM dimmer) and button (one-shot) actions. Their duty and frequency readout uses whole periods with interpolated edges (`of_instruments::stats::pwm_duty_freq_periods`); the existing demos keep their readout. Each edge is timed where the timing capacitor's ramps meet (`pwm_duty_freq_ramp`), so the readout is within 0.5 points and 1 % at every pot setting on the 50 µs grid.
- **555 schematics and instruments on the desktop:** house-style layouts in the three 555 files (no wiring invariant violations, the dimmer at every wiper position), a dedicated 555 painter that draws whatever the file lays out, and the scope and multimeter panel driven from each file's `[[instrument]]` tables. The dimmer is laid out the classic way (R1 from VCC to DISCH, the pot's wiper on DISCH, the steering diodes from the pot ends to the THRES/TRIG/C1 node, C1 to GND below) with no wire crossings; in all three, C2 on CONT taps the GND bus with a junction instead of crossing it (the one-shot keeps one hop, where its trigger pull-up passes the timing node). Route goldens `goldens/ne555-*.routes.txt` pin the three layouts.
- **ESP32-C3 555 clock counter demo** (`esp32c3-555-clock`, in the desktop picker): a 555 astable on a 5 V board, an AMS1117-3.3 LDO for the C3 and a 10k/33k divider into GPIO4, with our own direct-boot firmware (`firmware/esp32c3-clock-counter`, built from source with zig like the other assembly images) that counts rising edges from a GPIO interrupt over 100 ms gates and prints `freq: … Hz` on UART0. The file has a scope, a logic analyser on the clock and TX and a UART console; the 555 painter draws the C3 and LDO as boxes, a route golden (`goldens/esp32c3-555-clock.routes.txt`) pins the layout and a session test checks the printed frequency against the scope within 0.2 %. CI rebuilds the firmware and diffs it.
- **555 demos in the desktop picker** (`kind::PICKER`), with meter probe points on every routed pin of the file (the ground net is node `0`), so voltmeters and ammeters place on them as on the other demos.
- **Blink's desktop sampling keeps the grid:** the blink loop jumped to the end of an advance when its sample clock missed a grid instant (458 of 599 samples after an off-grid stop, 668 of 999 over 60 Hz frames). It now runs the grid-safe loop of the 555 demos; the blink E5d face at 12 ms and the blink meter readings at 16 ms are re-pinned (they now see the LED lit at 0.95 ms). The parity trace goldens are unchanged.
- **1N4148 diode part** (`onsemi.1n4148`, onsemi 1N914/D Rev. 6) and the `rust:diode` model, and the `ne555-pwm-dimmer` demo: the classic two-diode duty control, a 10 kohm pot splitting the timing resistance (about 18 % to 91 % duty at about 1 kHz).
- **NE555 timer part** (`ti.ne555`, `parts/timers/ne555`): an original Ohmforge macromodel from TI SLFS022K with the 5 kΩ divider (CONT moves both thresholds), threshold and trigger comparators, an SR latch with RESET priority (0.7 V), a saturating discharge transistor, the VOH/VOL output drops, supply current and pin bias currents. Datasheet checks through the parts bridge cover the astable frequency and duty cycle, the 1.1 RC monostable, RESET and CONT (`crates/of-components/tests/ne555_datasheet.rs`).
- **Logic analyser, `d(..)` signals and UART console (engine E5g, #49):** `d(REF.pin)` reads the pin's net voltage through a logic input (ideal: one 1.65 V threshold; real: V_IL/V_IH, holding its state in between); the Saleae Logic 8 profile (`parts/instruments/saleae.logic8/instrument.toml`: 8 channels, 1 MΩ ‖ 10 pF, V_IL 0.6 V, V_IH 1.2 V, 100 MS/s on up to 3 channels down to 25 MS/s on 8, from Saleae's data sheet and support pages) loads each probed net and samples edges on its clock (`of_instruments::logic`); `ohmforge run --log` writes `d(..)` columns (VCD `wire` variables); `of_instruments::uart::UartDecoder` decodes 8N1 at a `uart` instrument's `baud` and `ohmforge run --uart` prints each console's text; the ESP32-C3 drives GPIO21 (U0TXD, datasheet v2.5 Table 2-4) with UART0's frames at the configured baud when GPIO21 is wired, so a console on it reads the chip's serial output; the desktop shows a circuit's consoles and logic analysers under the serial monitor; `circuit check` limits a `uart` to `d(..)` TX/RX probes and checks `baud` and `sample_rate`.
- **Real-world instrument profiles and loading (engine E5f, #49):** `of_instruments::profile` holds the Fluke 87V (DC V and DC A ranges, 6000 counts, autorange, `OL`, ±(% + counts) bands, 10 MΩ input, 100 µV/µA, 1.8 mV/mA and 0.03 V/A burdens, from the 80 Series V Users Manual), the Rigol DS1054Z (V/div ÷ 25 code step, 8-bit clipping, gain and offset band, 1 MΩ ‖ 15 pF input) and the Rigol DP832 readback (10 mV / 1 mA, per-channel band). An `[[instrument]]` with `profile = "fluke.87v"` or `"rigol.ds1054z"` re-elaborates the circuit with its input (`of_circuit::loads`): a 10 kΩ/10 kΩ divider at 3.3 V reads 1.6492 V through the 87V, and a `dc_a` meter puts its burden in series with the measured pin (multimeter `params.input` = `uA`, `mA` or `A`). Ideal instruments add nothing. `circuit check` accepts these profiles on the matching kind. The figures are data in `parts/instruments/<vendor>.<model>/instrument.toml` (CC-BY-SA-4.0, a `source` on every table), embedded and parsed by `of_instruments::profile`. The desktop has a Profiles row (Ideal by default) for the meters (`1.649 ± 0.002 V`, `OL`), the LED scope (8-bit trace, step and band note) and the PSU readout (DP832 readback with bands).
- **Instruments in circuit files and `ohmforge run --log` (engine E5e, #49):** circuit files take an optional `[[instrument]]` table (RFC 0004; `format` stays 1): a multimeter (`mode = "dc_v"` or `"dc_a"`), scope, logic analyser, logger or UART console with a ref (`XMM1`), probes by `[[probe]]` name or inline signal, an optional profile (`"ideal"`, the default; real-world profiles come in E5f), schematic `at` and scope `params` (`time_div`, `trigger`, `level`). `ohmforge circuit check` now parses and resolves every probe and instrument signal against the file and the parts library and reports bad ones with line and column (unknown nets or parts, a missing pin, `i(U1)` on a part with more than two pins, wrong case, or a signal that does not suit the instrument, such as `i(..)` on a DC-volts meter). `ohmforge run <file.circuit.toml> --log FILE.csv` (or `.vcd`, `real` variables) logs the file's probes, named after them, and the instruments' inline signals on the `--step` grid; on blink the `LED current` column equals the solver's `i(R1)` within max(1 nA, 1 ppm). The five demos now carry an ideal ammeter (`XMM1`) and scope (`XSC1`) on `LED current`. `[[probe]]` names must be unique, and `ProbeEntry`'s `name` and `signal` keep their position (`name()`, `signal()`).
- **Desktop demos from circuit files (engine E4c, #48):** `of-app --circuit-files` (or `OF_CIRCUIT_FILES=1`, or `circuit_files = true` in the preferences) draws and runs the five desktop demos from the embedded `circuits/demos/` files on the engine `Session`. The schematic is built from each part's `[schematic]` geometry and is identical to the hand-wired board (routes byte-identical to the wiring goldens), and the LED current, scope, PWM, UART, PSU and meter readings match the hand-wired demos within `max(1 nA, 1 ppm)`. The hand-wired boards stay the default until E4d. `Session::terminal_currents` (per-pin currents for the meters), a switch `bounce_seed` host param and `of_circuit::demos::parts` (the embedded parts the demos use) support it; the parity tests now run the desktop's own `SessionSim`.
- **Demo circuit files and `ohmforge run` for them (engine E4b-2, #48):** the five desktop demos are now circuit files in [`circuits/demos/`](circuits/demos) (`blink`, `dimmer`, `fade`, `button`, `button-irq`; CC-BY-SA-4.0), with firmware by path and SHA-256, `ground = "gnd"`, and the board's schematic geometry, ids and labels. `of-circuit` builds a file into an `of_engine` session through the model registry (`build`, feature `engine`), with an in-memory `EmbeddedResolver`, the embedded demo files and firmware (feature `demos`) and the fetched-ROM lookup in `FsResolver` (feature `fs`, moved from the desktop app; same folders and `OF_REQUIRE_ESP_ROM` behaviour). Errors point at the line and column of the unknown part or pin or the wrong hash (with the actual hash). `ohmforge run <file.circuit.toml>` runs a circuit headless (`--until`, `--step`, `--out` CSV of every net voltage and probe, `--vcd`, `--uart`). Built from the files, all five demos match the legacy trace goldens and the hand-wired demos at the accepted tolerances, and the file names (refs, schematic ids, pin ids and names, net and terminal order) match the hand-written boards exactly. **Readout change:** the shipped files keep the ESP32-C3's true-to-life 5 mA idle draw (`quiescent_a = 0.005`), so the PSU current of a demo run from its file reads about 5 mA higher than today's desktop demos (the rail about 0.5 mV lower); the reviewed `blink.idle-draw` golden records it, and parity runs turn it off. CI checks `circuit fmt --check circuits` and `circuit check circuits`, and builds `of-circuit` with `engine,demos` for wasm32. The desktop app does not load the files yet (E4c).
- **Engine session and model registry (engine E4b-1, #48):** `of-engine` gains `Registry` (model strings such as `rust:led` to constructors) and `Session`, which builds the analog engine, attaches every component, registers CPU engines first, catches up to a pre-booted chip and runs with component timers, host parameters (pot `position`, switch `closed`, PSU set points) and commits. The pot and push button now change the circuit at run time, with the push button's contact bounce played by the component; the bench PSU really switches to constant current at its limit (`commit_with`). `Esp32c3Component` boots from an ELF, the ROM or a pre-booted chip and takes `quiescent_a`, `inputs` and `cpu_mhz`. New `bench.psu` part. The component API gains `ParamValue`, `attach`, `commit_with` and `ElabCtx::device_ref` (RFC 0001 addendum). The legacy blink, dimmer, fade, button and button-irq demos are recorded as trace goldens, and the same circuits built through the registry and run on `Session` reproduce them: blink, fade and both button demos byte for byte, the dimmer with identical digital output and a PSU current within 3.5 nA (the engine's U1 adds a 1 GΩ pad on the ADC pin GPIO2). Against the Linux-recorded goldens, samples taken on LEDC edges get 1 % (other platforms' libm moves them), and every run is also checked against the hand-wired demo on the same machine at the RFC 0003 tolerances. E4b-2 follows: circuit-file builder and embedded/fs resolvers, the five `circuits/demos` files with SHA-256, the idle-draw golden, parity from the files, `ohmforge run <file.circuit.toml>`, the CI `circuit fmt --check circuits` step and ref/pin naming reconciliation.

- **Circuit file format (engine E4a, #48):** [RFC 0003](rfcs/0003-circuit-file.md) defines `*.circuit.toml` (`format = 1`): parts with typed parameters, firmware by path and SHA-256, nets in router order, per-instance schematic geometry, ground symbols, keepouts with notes and probes. ### Fixed

- **PSU return and current readout (#45, closed by #54):** the bench supply is a two-terminal source. Its symbol now has explicit + and − pins, and − is routed to the common GND net on every demo (dimmer, fade, blink, and the push-button boards), with the GND label moved clear of the PSU box and a wiring invariant (`label-on-body`) that flags labels straddling a part's edge. The electrical model already placed the source between `vdd` and node 0, with GPIO high-side drivers sourcing from that rail, so LED current does return through the instrument; a KCL test checks that the current out of + equals the current into − and matches the LED plus pot divider. The face and sidebar now show the period-averaged rail current, so a snapshot during the PWM-off half no longer looks like only the 10 kOhm pot (0.33 mA) while the LED averages ~2.6 mA. The ESP32-C3 core supply current is not modelled.
- **Dimmer LED current chatter (#45, closed by #54):** the averaged LED-current trace used a 2 ms sliding window over 50 us samples, so a constant-duty 1 kHz PWM beat against the window and showed about +/- 0.2 mA of ripple. The display average is now a boxcar over two whole PWM periods, aligned to rising edges, and dimmer/fade also record a sample at each LEDC edge. At constant duty the averaged trace stays flat (ripple bound in tests); no extra noise is added.
- **Dimmer scope header:** the live "wiper … V" readout no longer overlaps the time/div control at 980×720 or narrower. The wiper value sits on a second row under the caption; the blink and push-button scope headers were checked for the same clash.
- Clippy warnings in `of-analog` (#2), and riscv-tests CI runs with a stale cache (#7).
